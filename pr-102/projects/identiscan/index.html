Identiscan

Check-in/out engine on top of dlib face matching, with GridFS photos and cascade-safe admin.

ReactTailwindCSSNode.jsFlaskMongoDBElectronJS
GitHub ↗

Architecture

Key decisions

Face matching lives in its own service
Flask + dlib sits behind /compare on :5004 while Express keeps the records. The matcher can be redeployed, or swapped for another model, without touching attendance rules or the admin app.
The capture is forwarded, never stored
Only the enrolled photo lives in GridFS; the live photo arrives as an express-fileupload buffer and is appended straight into the compare request (backend/controllers/mark.js:47-53, 73-82) — no write path puts a check-in photo on disk.
Rules live in the API, not the kiosk
Check-in before 12:00, checkout after a 6-hour gap and one in/out pair per day are enforced server-side, so editing the kiosk app cannot talk it into marking someone present.

The problem

Paper registers and proxy attendance don’t scale for large batches. The goal: walk up, enter a roll number, show your face, and get a trustworthy check-in — with admins able to see who was actually present, per class, per day.

What I built

Three services behind two frontends. The Attendance app takes a roll number plus a live photo (with a custom on-screen virtual keyboard for touchscreens) and POSTs to Express, which pulls the enrolled photo from a GridFS bucket and forwards both images to a Flask microservice. Flask runs the face_recognition pipeline — dlib 128-d embedding, Euclidean distance, 0.6 threshold, first face only — and returns the match distance. On match, Express writes the record.

The rules engine is where the domain lives: check-in before 12:00, checkout only after a 6-hour gap, one in/out pair per day, and attendance percentage computed against active class dates. The Admin app manages the hierarchy (batch → class → student) with cascade deletes wired as Mongoose hooks, so removing a batch can’t orphan records. Auth is session-cookie + bcrypt, and the whole Attendance frontend ships wrapped as a Linux Electron app for kiosk hardware.

On the accuracy number

Matching runs on dlib’s ResNet embedding (99.38% on LFW, per the model publisher). That’s the library’s benchmark, not an in-repo evaluation — the right way to read it is “proven model, threshold tuned for the deployment,” not a claim about our hallways.

Where it stops

Sessions and bcrypt exist, but no route is guarded yet, so auth is scaffolding rather than enforcement. Enrolled photos also outlive a student deletion — cascade deletes clean the records, not the GridFS bucket. Both are why this is a “worked in the hallway, not deployed” project rather than a shipped system.
